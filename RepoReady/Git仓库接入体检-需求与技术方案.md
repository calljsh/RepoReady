# Git 仓库接入体检：需求与技术方案

## 1. 项目背景与需求

### 1.1 项目背景

**目前的现状：**团队接入一个外部 Git 仓库时，通常要先人工阅读 README、查找依赖和启动方式，再排查平台专用脚本、硬编码路径及敏感信息。公开仓库数量多、结构各异，这些检查往往依赖接入人员的经验。

**产生的问题：**人工检查耗时，而且容易遗漏。一个项目可能文档齐全，却只能通过 Windows 脚本启动；也可能存在本机绝对路径或误提交的 `.env` 文件。问题通常要到部署、集成甚至安全审查时才暴露，增加返工成本。

**项目的意义：**RepoReady 将接入前的基础检查标准化。用户输入仓库链接，就能看到基于具体 commit 的就绪度评分、主要风险及其文件位置，从而更快判断“能否接入、需要先解决什么”。它是接入决策的辅助工具，不能替代人工审查或专业安全扫描。

### 1.2 面试题原文

> **题目：Git 仓库接入体检 · 48 小时实战题**
>
> **任务：**在 48 小时内完成 Git 仓库“接入体检”工具。
>
> **需求：**提供 Web 页面，用户只需输入一个公开 Git 仓库链接（至少支持 GitHub），工具自动分析并识别：
>
> - README、依赖清单、启动脚本的完整度；
> - Windows 专用脚本（`.bat` / `.cmd` / `.ps1` / `.vbs`）；
> - 硬编码路径（`C:\`、`/Users/`、绝对路径等）；
> - 密钥与敏感信息风险（`sk-`、`AKID`、`Bearer`、私钥、`.env` 入库等）。
>
> 用可视化形式展示上述结果，并给出**接入就绪度评分**和**主要风险清单**。
>
> 加分项：结合 AI 给出项目评分或接入建议。
>
> **要求：**
>
> 1. 核心功能可以跑通。
> 2. 不限技术栈，鼓励使用 AI Coding 工具。
> 3. 提交结果时，请直接提供 GitHub 仓库地址。
> 4. 其他：可以附加提供 Vibe Coding 过程中的提示词或截图；建议附一份 `AI_USAGE.md`，说明用了哪些 AI 工具、如何验证其输出，至少包含 1 条「AI 答错但被你发现」的记录。
> 5. 更新跟踪（设计说明即可，不强制实现）：如果原仓库后续有代码更新，你的工具如何发现并更新报告？请在 README 中说明：怎么发现更新、怎么避免全量重算、报告如何标注所基于的 commit、失败或限流时怎么兜底。

### 1.3 项目目标与报告内容

本项目是一道 48 小时 AI 工程面试实战题。目标是交付一个可以现场演示的 Web 小产品：用户输入公开 GitHub 仓库链接，系统分析该仓库的接入准备情况，生成可解释的报告，帮助接入方快速发现文档、启动方式、跨平台兼容性和敏感信息方面的风险。

核心使用流程：输入仓库 URL → 校验并定位默认分支的最新 commit → 获取该 commit 的文件清单和必要的文本内容 → 执行规则检测与评分 → 在页面展示报告。

报告至少包含：

- 接入就绪度总分（0–100）及分项得分、扣分原因。
- README、依赖清单、启动脚本的完整度。
- Windows 专用脚本（`.bat`、`.cmd`、`.ps1`、`.vbs`）的位置。
- 典型硬编码绝对路径的位置。
- 疑似密钥、私钥、授权信息和 `.env` 入库风险。
- 按严重程度排序的主要风险清单，包含文件路径、行号（适用时）、影响与整改建议。
- 仓库、分支、完整 commit SHA、扫描时间、规则版本及扫描覆盖情况。

规则命中表示“疑似风险”，不等同于确认泄露。任何疑似凭据原值都不得出现在 API 响应、页面或日志中。

## 2. 技术栈

| 部分 | 选型 | 用途 |
| --- | --- | --- |
| 后端 | Java 8、Spring Boot 2.3.12.RELEASE | HTTP API、扫描编排与报告生成 |
| HTTP 客户端 | Spring `RestTemplate`（配置连接/读取超时） | 调用 GitHub REST API |
| 数据校验 | Bean Validation（JSR-303） | 校验输入；GitHub 主机与路径另做严格白名单校验 |
| 测试 | JUnit 5、Mockito、Spring Boot Test | 规则、评分、脱敏、GitHub 响应与异常分支测试 |
| 前端 | Vue 3、Vite、ECharts | 输入页、扫描状态、分项图表与风险清单 |
| 持久化 | 首版不引入数据库 | 单次请求生成报告，降低 48 小时交付复杂度 |

后端按 facade（HTTP）、domain-service（扫描流程与评分）、manager（仓库数据整理和转换）、infrastructure（GitHub API 客户端）、DTO/VO 分层。扫描规则采用独立接口及实现，便于单独测试和扩展；不为首版引入不必要的数据库层。

## 3. 需求边界与验收

### 本次必须实现

1. 只接收标准公开 GitHub 仓库 URL，例如 `https://github.com/owner/repo`，可兼容末尾 `/` 和 `.git`。不接受任意 Git URL、本地路径或私有仓库认证输入。
2. 只扫描默认分支在开始扫描时解析到的**一个固定 commit**，避免抓取过程中仓库更新造成报告内容不一致。
3. 检测 README、常见依赖清单和启动入口的存在性及基本可用性；识别 Windows 专用脚本；扫描文本中的典型绝对路径和疑似敏感信息。
4. 设置文件数量、单文件字节数、总读取字节数、请求超时和扫描耗时上限；跳过二进制、生成目录及超限文件。报告准确标记跳过数量和“部分扫描”，不得将未扫描视为无风险。
5. 页面提供输入、扫描中、成功报告和失败提示四种状态；图表展示总分和分项，风险列表可按严重程度浏览并查看证据位置。
6. 评分采用确定性规则，分项权重与扣分依据固定并可追溯；主要风险按严重程度排序。敏感内容在生成 DTO 前脱敏，日志也不输出原始文件内容。
7. README 写明启动方式、演示样例、检测边界及下述更新跟踪方案；`AI_USAGE.md` 记录 AI 工具用途、人工验证过程和至少一条发现并纠正 AI 错误的真实记录。

### 本次不做

- GitLab/Gitee、多分支、自定义 commit、私有仓库、仓库代码执行或依赖安装。
- 全量漏洞扫描、依赖 CVE 审计、历史 commit 秘钥搜索；本工具只分析当前快照中的有限文本文件。
- 用户账户、历史报告管理、自动定时更新及 GitHub Webhook 的实际实现。
- AI 评分或建议属于加分项，核心功能稳定后再考虑；确定性评分不依赖模型。

### 验收标准

- 输入两个结构不同的公开仓库，能生成不同且可解释的报告，均显示所依据的 commit。
- 用仅含**假测试凭据**的样例验证敏感信息命中；检查 API 响应、页面及日志均不包含凭据原值。
- 无效 URL、仓库不存在、GitHub 限流、文件树不完整和扫描超限均有明确反馈或覆盖标记。
- 规则、评分与脱敏的关键逻辑有单元测试；按项目要求评估并达到新增核心代码至少 80% 的单元测试覆盖率。

## 4. 核心需求涉及的 API（代码 review 清单）

### 4.1 本产品对前端提供的 API

| API | 入参 | 返回重点 | Review 要点 |
| --- | --- | --- | --- |
| `POST /api/reports/scan` | JSON：`repositoryUrl` | 报告 ID（可选）、仓库信息、commit、总分、分项、风险、覆盖情况 | URL 白名单；超时；错误码；返回值和日志脱敏；避免长时间无反馈 |
| `GET /api/health` | 无 | 服务状态 | 可选，但便于本地演示与部署检查 |

首版可以让 `POST /api/reports/scan` 同步返回报告。若真实仓库扫描耗时使 HTTP 超时，再改为创建扫描任务、轮询状态；不要在没有证据前提前引入任务队列。

### 4.2 后端调用的 GitHub REST API

API 根地址：`https://api.github.com`。仅向固定 GitHub API 主机发请求，不依据用户输入拼接任意请求主机。请求应设置 `Accept: application/vnd.github+json`、`X-GitHub-Api-Version`、合理的 `User-Agent`；可选使用服务端环境变量提供的 Token，绝不将其返回前端。

| 顺序 | GitHub API | 用途 | 重点检查 |
| --- | --- | --- | --- |
| 1 | `GET /repos/{owner}/{repo}` | 验证公开仓库并取得 `default_branch` | 404/私有仓库、归档仓库、仓库元信息；限制 owner/repo 格式 |
| 2 | `GET /repos/{owner}/{repo}/commits/{branch}` | 将默认分支解析为固定的完整 commit SHA | 后续请求使用 SHA，不再依赖可移动的分支名 |
| 3 | `GET /repos/{owner}/{repo}/git/trees/{tree_sha}?recursive=1` | 获取该 commit 的文件清单、路径、类型、大小和 blob SHA | 检查响应的 `truncated`；截断时不能声称完整扫描 |
| 4 | `GET /repos/{owner}/{repo}/git/blobs/{file_sha}` | 按规则需要读取文本文件内容 | 处理 Base64 编码、大小限制、二进制/无效编码和请求失败 |

第 2 步的 commit 响应中可取得关联 tree SHA；第 3 步以该 tree SHA 为准。读取 blob 前先根据路径、类型和大小筛选，避免逐个下载整个仓库。README/清单/脚本等候选文件优先读取；其他文本文件在扫描预算内读取。`recursive=1` 返回 `truncated: true` 时，标记部分扫描；如要支持超大仓库，可在后续版本改为逐层遍历 tree。

GitHub API 文档：

- 仓库：[Get a repository](https://docs.github.com/en/rest/repos/repos#get-a-repository)
- Commit：[Get a commit](https://docs.github.com/en/rest/commits/commits#get-a-commit)
- Tree：[Get a tree](https://docs.github.com/en/rest/git/trees#get-a-tree)
- Blob：[Get a blob](https://docs.github.com/en/rest/git/blobs#get-a-blob)
- 限流：[Rate limits for the REST API](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)

### 4.3 API 调用安全与失败处理

- GitHub URL 解析后只保留 `owner`、`repo`；严格校验字符与长度，拒绝凭据、端口、查询参数、片段及非 `github.com` 主机，防止 SSRF 和路径混淆。
- 对 GitHub 的 403/429 及 `X-RateLimit-Remaining`、`X-RateLimit-Reset`、`Retry-After` 做明确处理；页面提示稍后重试，不把限流当成“仓库无风险”。
- 404 返回“仓库不存在或不可公开访问”；网络超时与 5xx 返回可重试错误；局部 blob 失败时标记部分扫描并记录失败文件数。
- 限制扫描资源消耗；不执行仓库中的任何脚本，也不克隆后运行项目。外部文本仅作为待分析数据，不能作为指令执行。

## 5. 更新跟踪设计（仅写入 README，不要求实现）

未来定时读取默认分支最新 commit SHA，与最近一次报告的 SHA 比较；相同则复用报告。不同则比较两个 commit 的文件变化，只重新获取和扫描新增或修改的文件，移除被删除文件的旧结果，再重算受影响的汇总和分数。报告应记录仓库、分支、完整 commit SHA、扫描时间和规则版本。若规则版本变化，即使 commit 未变也需要重算受影响规则。GitHub 限流或更新失败时保留上一份成功报告，但明确标注“历史报告、最新状态未确认”，按退避策略重试。
